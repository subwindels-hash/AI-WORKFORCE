## Summary

Fixes the reported **`apollo.io ✕ Connection failed`** in Admin → API Management
and makes the Apollo.io Lead Discovery provider work against the API as it is
documented today (https://docs.apollo.io/reference/apollo-api).

PR #72 moved Apollo to `x-api-key` header auth and the `auth/health` ping, but
the badge still failed. Two things were still wrong, and both are documented
Apollo behaviour rather than guesses:

**1. Apollo API keys are scoped per endpoint, and `auth/health` alone is not a
valid verdict.**

> "**Scoped key (default)**: You pick the specific endpoints the key can access,
> and it only works for those. If you use it to call an endpoint you didn't
> select, Apollo returns a `403` error." — https://docs.apollo.io/docs/create-api-key

So a key created for `mixed_people/api_search` (the endpoint this app actually
calls) can answer **403 on `auth/health`**, and the old test turned that into
`Invalid API key or plan without API access` → red `✕ Connection failed` badge,
for a key that works.

**2. The runtime adapter called the retired endpoint first, and treated 403 as
fatal.** `mixed_people/search` was deprecated and replaced by
`mixed_people/api_search` (enforcement began 15 Dec 2025); it answers `403
API_INACCESSIBLE` for current keys. The adapter tried it **first** and its
fatal-status list contained `403`, so Lead Discovery aborted before ever
reaching the documented endpoint — the search failed even when the key was fine.

### Changes

**Connection test — `ApiProviders::testApollo()`**

- Two credit-free probes: `GET /api/v1/auth/health` (documented key check) and,
  only when that answers `403/404/422`, `POST
  /api/v1/mixed_people/api_search?per_page=1&q_keywords=apollo` — the endpoint
  Lead Discovery really calls. A key that passes probe 2 reports **Connected**
  and says it is scoped.
- `401` stays final (bad key); `422` on the functional probe counts as
  authenticated (Apollo's `422` is parameter validation, not auth).
- A `200` that is not Apollo answering is not a pass: `healthy=false`,
  `is_logged_in=false` and a non-JSON body (intercepting proxy / wrong base URL)
  each report their own reason instead of a false **Connected**.
- Every refusal now names the fix: missing endpoint scope / "Set as master key",
  free accounts needing a work-email signup, rate limit, Apollo outage.
- Transport failures are diagnosed instead of flattened into "Connection
  failed": `http()` now returns cURL's `errno`/`error`, so a missing CA bundle
  (`curl.cainfo` → cacert.pem), DNS failure and blocked egress (443) each report
  differently. Messages stay inside the 255 chars the row stores, fix first.
- Key hygiene: whitespace/newlines/quotes stripped, a pasted cURL command yields
  its `x-api-key` value, and a re-saved `••••` mask is reported as a mask rather
  than tested as a key.
- Base URL canonicalisation (`apolloApiRoot()`): `apollo.io` / `app.apollo.io`
  are not API origins, a pasted `/api/v1` is not doubled, `http://` is upgraded,
  markdown link wrappers are unwrapped.

**Runtime adapter — `LeadDiscovery\ApolloProvider`**

- `POST /api/v1/mixed_people/api_search` is now the **first and normal** call;
  the deprecated `mixed_people/search` is only a fallback when Apollo says the
  documented route does not exist for this key (`404/405/410`). `401/403/400/422`
  are never retried against the other route — they are reported with the scope
  that is missing.
- Transport failures keep cURL's own words (`cURL 60: SSL certificate problem: …`)
  so a Lead Discovery failure says CA bundle / DNS / blocked port, not just
  "timed out or could not connect".
- Error envelopes are parsed from `error_code`/`error_message`/`message`/`error`
  **and** from a `200 {"status":"error"}` body, which previously could be read
  as data.
- **Contact reveal (opt-in, credit-capped).** Apollo's search "doesn't return
  email addresses or phone numbers" — enrichment is the documented way
  (https://docs.apollo.io/reference/people-api-search). Person Mode filters on
  free-webmail domains, i.e. personal emails, so it cannot work without it.
  `POST /api/v1/people/bulk_match` is now used in batches of ≤ 10 ids, only for
  rows Apollo flags `has_email`/`has_direct_phone`, capped per search (default
  25, max 100), off by default, configurable per provider in Admin → API
  (`reveal_contacts`, `reveal_personal_emails`, `reveal_phone_number`,
  `reveal_limit`) or by env. A refusal (no credits / missing
  `people_bulk_match` scope / 429) degrades to the privacy-safe rows and is
  reported — it never fails the search.
- Locked placeholders are no longer stored as contacts:
  `email_not_unlocked@…`, obfuscated `j***@gmail.com` and `*`-masked phones are
  rejected (`ApolloProvider::isUsableEmail()`), so Person Mode cannot "match" a
  placeholder and leads never carry junk emails.
- Provider rows are resolved **per driver**: `lead_discovery` hosts both Google
  Places and Apollo.io, and `resolve()` returns only the active row. Apollo now
  reads its own row through the new `ApiProviders::resolveDriver()` /
  `resolveDriverForRequest()` (before, an Apollo row saved as *fallback* behind a
  primary Google Places row was invisible at runtime — and Google Places could
  be handed the Apollo key). `healthCheck()` distinguishes "never configured"
  from "configured but switched off".

**Surfaces**

- `/leads/search` returns `providerInfo` (`results`, `revealEnabled`,
  `revealRequested`, `revealed`) and a `notice` explaining that Apollo search
  carries no emails until reveal is on; the Leads UI shows it. Internal notes go
  to the CI error log — members still never see connection internals
  (`publicError()` untouched).
- The Admin API dashboard now prints the provider's own `last_test_message`
  under the badge, so a red badge says *why*.
- `.env.example` and `docs/LEAD_DISCOVERY.md` document scopes, endpoints, credit
  cost and a `✕ Connection failed` → cause → fix table.
- `application-deployment.zip` rebuilt with `tools/build_deployment_zip.py`
  (683 release files, `--check` passes) — cPanel deploys from this archive, so a
  stale bundle would ship the old code.

### Tests

- **new `tests/cases/112-apollo-connection-test.php`** (14 tests, no DB, staged
  transport): scoped-key 403→200 reports Connected, 401 is final, both-403 names
  the scope/master-key/work-email fixes and never echoes the key, 404 falls
  through, `is_logged_in:false` honoured, TLS/DNS/firewall each diagnosed, 429
  and 5xx honest, missing and masked keys explained, key hygiene (quotes,
  newlines, pasted cURL), base-URL canonicalisation, 422-probe, reveal scope
  note, and adapter/test endpoint agreement.
- **`tests/cases/84-apollo-lead-provider.php`** rewritten for the corrected
  contract (19 tests): documented endpoint called first and only, 404→deprecated
  fallback reported in notes, 401 and **403 not retried** with actionable text,
  `200 {"status":"error"}` envelope rejected, 429 retry then fallback, blank
  filters dropped, placeholder/obfuscated emails rejected, opt-in enrichment end
  to end (`details:[{id}]` body, `reveal_personal_emails=true`, merged
  name/email/phone/LinkedIn/address, `enriched`/`privacy_safe` flags), the credit
  cap (12 rows, limit 10 → one batch of 10), enrichment refusal degrading
  gracefully, and reveal staying off unless an operator switches it on.
- **`tests/cases/70-api-providers.php`** +2 DB tests: driver-scoped resolution
  (Apollo as fallback behind a primary Google row resolves its own key and never
  the Google one; disabled rows are not served but stay diagnosable) and an
  end-to-end `ApiProviders::test()` run of the scoped-key path.
- Not executed here: this sandbox has no PHP binary and no outbound network
  (`curl` to any host fails at the TLS handshake), so the suites could not be
  run and Apollo could not be called live. The endpoint/auth/scope behaviour is
  taken from Apollo's current docs and OpenAPI definition; the tests are staged
  against the injectable transports (`ApiProviders::$http`,
  `ApolloProvider::request()`).

### What an operator still has to do

If the key itself is the problem, the badge now says which problem: regenerate a
deleted/expired key, grant it the `mixed_people/api_search` scope (plus
`people_bulk_match` for reveal) or toggle **Set as master key**, and note that
free Apollo accounts registered with a personal address (gmail/outlook/…) cannot
use these endpoints at all. To get emails/phones in Person Mode, switch on
**Reveal emails/phones** for the Apollo.io provider — that spends Apollo credits
(1 per record) and is capped per search.
